# scene-mock

基于「项目 ⊃ Scene ⊃ 接口返回值」的 Mock 接口代理管理方案

把 mock 数据从 whistle values 中剥离，用「项目 + 接口池 + Scene」结构化管理：whistle 代理按项目维度组织，选定项目后在该项目下新建场景，在场景下维护每个请求的具体返回值，切换场景不丢数据。

## 1. 背景、用户与痛点

前端日常联调常借助 whistle 做代理并 mock 接口返回。随着接口数量增长、同一接口的返回场景变多，「在 whistle values 里维护所有变量」的模式暴露出两个核心痛点。

### 1.1 目标用户与使用场景

| 角色 | 说明 |
| --- | --- |
| **主用户 · 前端开发** | 本地联调、后端未就绪时独立开发、验证空列表 / 异常 / 慢接口。一天内会在多种返回之间反复切换。 |
| **次用户 · 测试 / QA** | 用预制 Scene 复现固定数据态（缺货、支付失败、空购物车），减少口头对数据、反复改 mock。 |
| **非目标** | 不替代 YApi / Apifox / Postman 做接口文档与全量测试；不做团队权限、云端托管、契约测试平台。 |

典型场景：

- **异常流联调**：同一套下单接口，在「正常」「库存不足」「支付超时」之间来回切，测完要能立刻回到正常数据。
- **部分真实、部分 mock**：只 mock 尚未就绪或需要造数的接口，其余走真实环境。
- **多项目并行**：一个前端仓库要同时联调多个后端域名（如 `microcredit-ms-test-c.jhjj.paas.test` 与本地 `localhost:8889`），每个域名的接口集合与透传目标各不相同。
- **团队复用**：把「空数据联调」「下单异常流」提交到 git，新成员 clone 即可用，不必每人重写一份 values。

### 1.2 核心痛点

**痛点 ① · 接口多，values 维护繁琐**

所有接口的 mock 数据都堆在 whistle 的 values 变量里。接口一多，变量列表臃肿、命名混乱、查找困难；接口增删改没有结构化管理，全靠手动在规则和 values 之间来回切换，极易出错且难以沉淀。

**痛点 ② · 多返回值场景改数据易丢失**

同一个接口往往有多种返回场景（正常 / 空列表 / 异常 / 慢接口）。在 whistle 里改 mock 数据时，**新场景覆盖旧场景**——想回到上次的返回值得重新编辑，上一次的 mock 数据无声丢失。联调异常流时尤其痛苦：改完异常数据还得手动改回正常数据，频繁切换、容易忘切回。

**痛点 ③ · 多域名代理配置散落**

联调对象往往不止一个后端域名。每个域名的转发规则、透传目标分散在 whistle 规则与手写备注里，换项目、换环境时要逐条核对修改，规则之间互相影响，谁代理谁、未命中去哪全凭记忆。

## 2. 解决思路

痛点的根因相同：**whistle 既承担「请求转发」又承担「数据存储」，职责过载，且数据扁平堆叠、缺乏「项目」与「场景」这两层抽象**。

> **核心理念：mock 数据与代理解耦，代理按项目维度组织**
>
> 把 mock 数据从 whistle 的 values 中完全剥离，由独立的 mock 服务统一管理；whistle 退回到单一职责——**只负责把请求转发到 mock 服务**。转发规则不再全局混排，而是按「项目」生成：一个项目对应一对域名（被代理的域名 → 代理到的域名），一条 whistle 规则。数据管理与请求代理各司其职，代理配置与业务数据都挂在项目下。

基于此理念，建立三个基础对象来分别击破痛点：

| 对象 | 说明 |
| --- | --- |
| **项目（Project）** | 一组代理配置的最小单元：`被代理的域名 → 代理到的域名`。每个项目生成一条 whistle 规则（被代理域名进 mock 服务），未命中请求透传到该项目自己的「代理到的域名」。 Scene、接口池都归属某个项目。→ 解决痛点③ |
| **接口池（API Pool）** | 项目级接口注册表，集中管理该项目域名下的接口定义（`method + URL 模式`，支持 `:param` 路径参数）。结构化、可检索，告别 values 里的扁平堆叠。→ 解决痛点① |
| **Scene（场景）** | 项目下「一组接口 + 每个接口返回值」的集合。启动一个 Scene 即同时激活其下所有接口的代理。同一接口可在多个 Scene 中有不同返回值，互不覆盖。→ 解决痛点② |

工作方式：**先选择项目 → 在该项目下新建 Scene → 在 Scene 下为每个请求设定具体返回值**。

## 3. 概念模型

### 3.1 三个基础对象与层级

层级关系：**项目 ⊃ Scene ⊃ 接口条目**；接口池是项目内的共享注册表，被该项目所有 Scene 引用。

| 对象 | 职责 | 示例 | 解决 |
| --- | --- | --- | --- |
| **项目** | 代理配置单元：被代理域名、代理到的域名、whistle 规则 | `microcredit-ms-test-c.jhjj.paas.test → http://localhost:8889` | 痛点③ |
| **接口池**（项目内） | 该项目接口定义注册表（method + URL 模式 + 描述） | `GET /api/users/:id` | 痛点① |
| **Scene**（项目内） | 一组「接口 + 各自返回值」的组合，可命名、可启动 | 正常下单 / 下单异常流 / 空数据联调 | 痛点② |

明确不再加第四层（如 Profile / 场景组合快照）：**Scene 本身就是可激活的接口集合**。需要并行覆盖多条业务线时，在项目内同时激活多个 Scene，而不是再套一层容器。不同项目之间天然并行——各项目的 whistle 规则互不干扰，各自的激活 Scene 独立生效。

### 3.2 Scene 的组成单元

每个 Scene 由若干**接口条目**构成，一条 = `{ 接口引用, HTTP 语义, data 引用 }`：

- **接口引用**：指向本项目接口池中的某个接口（同一接口可被本项目多个 Scene 引用复用）
- **HTTP 语义**：该条目的 `status` / `delay` / `headers`，写在 Scene JSON 里
- **data 引用**：指向 `data/<api-id>/<variant>.json` 中的一份业务 body。同一接口可以有多份 variant（`list` / `empty` / `server-error`），不同 Scene 指向不同 variant 即互不覆盖；也可显式共用同一份

关键点：**同一接口在不同 Scene 里可以指向不同返回值，互不影响**。例如 `GET /api/orders` 在「正常下单」指向 `data/get-orders/list.json`，在「空数据联调」指向 `data/get-orders/empty.json`——切换 Scene 不删文件，上一次的 mock 数据完整保留。

### 3.3 运行时状态

对象之外，系统还维护一份运行时状态，决定「此刻哪些返回值真正对外生效」：

| 状态 | 说明 |
| --- | --- |
| **项目规则表** | 所有项目的「被代理域名 → 项目」映射，决定一个进入插件的请求归属哪个项目；持久化在各项目配置中 |
| **激活 Scene 集合**（按项目） | 每个项目各自维护 0～N 个无接口重合的激活 Scene；持久化在项目配置里，服务重启后恢复 |
| **生效路由表**（按项目） | 由该项目当前激活 Scene 的接口条目实时合成，供请求匹配使用 |
| **项目透传目标** | 项目的「代理到的域名」。未命中该项目生效路由的请求转发到这里，实现混合联调；为空则回源或 404 |

## 4. 产品形态与架构

scene-mock 是跑在开发者本机的轻量工具，不是云端平台。产品由四部分组成，其中 mock 服务是唯一运行时。

| 层级 | 说明 |
| --- | --- |
| ① 数据层 · `mocks/` | 纯 JSON 文件。项目列表、各项目的接口池 / Scene 定义 / `data/` 返回值 / 激活状态全部落盘，可 git 管理、可手改、可 diff。 |
| ② 服务层 · mock 服务 | 零依赖（或极少依赖）Node 进程。负责项目路由、请求匹配、返回 mock、未命中透传、文件热加载、管理 API。 |
| ③ 交互层 · Web 面板 | 主操作入口。管理项目 / 接口池 / Scene / 返回值 / 激活与冲突。与手改 JSON 双通道，写同一套文件。 |
| ④ 接入层 · whistle | 只做按项目生成的转发规则，不存任何 mock 数据。切换 Scene 不改规则；新增/删除项目才增减规则。 |

### 4.1 请求路径

```
浏览器 / App
    │
    ▼
whistle                    # 每个项目一条规则，例如 microcredit-ms-test-c.jhjj.paas.test scene-mock://
    │
    ▼
scene-mock
    ├─ 按请求 host 定位项目
    │     ├─ 命中该项目激活 Scene 的接口  →  返回该 Scene 下的 JSON（status / delay / headers / body）
    │     └─ 未命中                       →  透传到该项目的「代理到的域名」（如 http://localhost:8889）
    │
    └─ 管理面板与管理 API 与业务流量隔离
```

### 4.2 端口与进程约定

- 默认监听 `127.0.0.1:3456`，仅本机可访问，不对外暴露。
- 管理面板与 mock 共用同一端口：页面在 `/`，管理 API 在 `/__admin/*`，业务接口按原 path 匹配。接口池禁止注册 `/__admin` 前缀。
- 启动方式：`npx scene-mock` 或 `node bin/scene-mock.js`，工作目录下读取 `mocks/`。
- 端口占用时直接报错退出，不静默改端口（避免 whistle 规则指向空服务）。

## 5. 项目、接口池与 Scene 的维护方式

### 5.1 项目

项目是代理配置的顶层单元，也是面板管理的入口：**先选定项目，再管理其下的接口池与 Scene**。

| 操作 | 说明 |
| --- | --- |
| **新建项目** | 填写项目名、**项目 ID**（必填）、**被代理的域名**、**代理到的域名**。项目 ID 只能含英文字母、数字、`_`、`-`（以字母开头），全工作区唯一，用作 `projects/<id>/` 目录名。被代理域名生成一条 whistle 规则（`被代理域名 scene-mock://`）；代理到的域名是该项目未命中请求的透传上游，可留空（回源） |
| **编辑项目** | 可改名与两个域名。改被代理域名会同步改写 whistle 规则；改代理到的域名即改该项目的透传目标 |
| **进入项目** | 在项目管理页点击项目的「Scene / 接口池」进入对应页面；面板不设全局「当前项目」，Scene 管理与接口池页内可直接选择任意项目操作其数据 |
| **删除项目** | 删除该项目全部配置（接口池、Scene、data）并移除其 whistle 规则；二次确认并列出影响范围 |

约定：

- 被代理域名写 host 即可（如 `microcredit-ms-test-c.jhjj.paas.test`），可带协议便于阅读，生成规则时去掉协议。
- 不同项目的被代理域名不能相同；同一 host 只属于一个项目。
- 直接请求 whistle 自己的监听端口仍进管理页，即使写进项目也不会被劫持。

### 5.2 接口池

接口池是**项目内**唯一的接口定义注册表。Scene 只引用接口 id，不复制 method / URL。改 URL 模式只需改一处，该项目所有引用该接口的 Scene 自动跟上。不同项目的接口池互不影响（不同域名的同名接口互不冲突）。

| 操作 | 说明 |
| --- | --- |
| **注册接口** | 填写 method、URL 模式、描述，生成稳定 `id`（可手改，项目内唯一）。支持 `:param` 路径参数，如 `/api/users/:id` |
| **编辑接口** | 可改 method / URL / 描述；`id` 一旦被 Scene 引用，改 id 视为重命名，需同步改各 Scene 的引用与 `data/<api-id>/` 目录名 |
| **查看引用** | 列出引用该接口的全部 Scene，删除前可感知影响面 |
| **删除接口** | 从接口池移除；若仍被 Scene 引用，先告警并列出 Scene 清单，确认后一并清理引用和 `data/<api-id>/` 目录 |

接口 `id` 建议用稳定语义名（`get-orders`），不要用 URL 原文——URL 常变，id 一变 `data/` 目录和所有 Scene 引用都要跟着改。

### 5.3 Scene

Scene 是「接口 + 返回值」的组合容器，归属某个项目。对它的增删改不污染接口池，也不影响其它 Scene 与其它项目。

| 操作 | 说明 |
| --- | --- |
| **新建 Scene** | 在所选项目下起名 + 归属业务流程（如「下单异常流」「空数据联调」），得到一个空容器。文件名即 Scene ID（`scenes/<id>.json`） |
| **添加接口条目** | 从本项目接口池选一个接口 → 设定 HTTP 语义，并新建一份 data variant（或复制其它 Scene 的 variant 为新文件） |
| **设定/修改返回值** | 改本条目的 status / delay / headers，以及它所引用的 data 文件。默认不动其它 Scene；若该 variant 被多个 Scene 共享，保存时先 fork |
| **复用接口** | 同一接口可被加进本项目任意多个 Scene；每个 Scene 默认指向独立 variant，也可显式共用同一份 |
| **复制 Scene** | 一键复制整个 Scene：以源 Scene 为底生成新 Scene（新 id），全部条目的 data 文件**复制为新 variant 集**（默认隔离，不共享文件），原 Scene 不改动。适合「从正常流复制一份再改异常」的日常增量 |
| **编辑** | 增删条目、调返回值、改 Scene 名与描述 |
| **删除 Scene** | 只删这个 Scene JSON；接口池、其它 Scene、以及仍被引用的 data 文件都保留 |

## 6. Mock 数据的 JSON 维护

概念确定后，所有数据以 JSON 文件方式维护在本地 `mocks/` 目录。核心设计原则：**一个项目 = `projects/` 下一个目录；一个 Scene = 一个 JSON 文件；一份业务 body = `data/` 下的一个 variant 文件**。同接口的多种返回作为独立 variant 并存，切换 Scene 不删文件、互不覆盖。

Web 面板与手改文件是同一数据源：面板写文件，文件变更由服务热加载。不引入独立数据库。

### 6.1 目录结构

```
mocks/
├── config.json                        # 全局配置：matchPatterns、unmatched 默认值
└── projects/                          # 每个项目一个目录
    └── microcredit/                   # 项目目录名 = 项目 id
        ├── project.json               # 项目配置：name、被代理域名、代理到的域名、激活 Scene
        ├── apis.json                  # 该项目接口池
        ├── scenes/                    # 该项目每个 Scene 一个 JSON
        │   ├── normal-order.json      # Scene A：正常下单
        │   ├── empty-data.json        # Scene B：空数据联调
        │   └── order-error.json       # Scene C：下单异常流
        └── data/                      # 该项目接口返回值（业务 body），按 api-id 分组
            ├── get-orders/
            │   ├── list.json          # 正常列表
            │   ├── empty.json         # 空列表
            │   └── server-error.json  # 500 对应的 body
            └── create-order/
                ├── success.json           # 创建成功
                └── validation-error.json  # 参数校验失败
```

> **目录即项目，文件即 Scene，variant 即返回值**
>
> **每个项目对应 `projects/<project-id>/` 目录**；项目下的代理配置、接口池、Scene、data 全部自包含，整体可拷给同事。
>
> **每个 Scene 对应 `scenes/<scene-id>.json`，文件名 = Scene ID**。Scene 只声明「用了哪些接口、HTTP 语义、指向哪份 data」，不内嵌业务 body。
>
> 业务 body 按接口聚合在 `data/<api-id>/<variant>.json`。同一个接口（如 `get-orders`）可以有多份 variant；三个 Scene 分别引用 `list` / `empty` / `server-error`——**切换 Scene 不删除任何文件**，上一次的 mock 数据完整保留。

### 6.2 五种文件类型

**`config.json`** — 全局配置（小）。whistle 规则的额外匹配前缀、未命中默认策略。

```json
{
  "matchPatterns": ["/api/"],
  "unmatched": "passthrough"
}
```

**`projects/<project-id>/project.json`** — 项目配置。代理域名对、该项目激活的 Scene 列表。激活切换回写此文件。

```json
{
  "name": "微贷后端",
  "host": "microcredit-ms-test-c.jhjj.paas.test",
  "target": "http://localhost:8889",
  "activeScenes": ["normal-order"]
}
```

| 字段 | 说明 |
| --- | --- |
| `name` | 展示名 |
| `host` | 被代理的域名。生成 whistle 规则 `<host> scene-mock://`；可带协议书写，规则里去掉协议 |
| `target` | 代理到的域名。未命中该项目路由时 `method + path + query + body` 转发到这里；空表示回源（或按 `unmatched` 404） |
| `activeScenes` | 该项目当前激活的 Scene id 列表 |

**`projects/<project-id>/apis.json`** — 接口池 · 项目内唯一。注册该项目接口的 method + URL 模式 + 描述，供 Scene 引用。

```json
[
  {
    "id": "get-orders",
    "method": "GET",
    "url": "/api/orders",
    "desc": "订单列表"
  },
  {
    "id": "create-order",
    "method": "POST",
    "url": "/api/orders",
    "desc": "创建订单"
  }
]
```

**`projects/<project-id>/scenes/<scene-id>.json`** — Scene 定义 · 每个 Scene 一个文件。声明名称、描述、接口条目（HTTP 语义 + 对 data variant 的引用）。`data` 字段是 variant 名，解析为 `data/<api-id>/<variant>.json`。

```json
{
  "name": "正常下单",
  "desc": "正常下单流程的接口返回值组合",
  "apis": {
    "get-orders": {
      "status": 200,
      "delay": 0,
      "headers": {
        "Content-Type": "application/json"
      },
      "data": "list"
    },
    "create-order": {
      "status": 201,
      "delay": 0,
      "data": "success"
    }
  }
}
```

`empty-data.json` 只改引用，不复制 body：

```json
{
  "name": "空数据联调",
  "desc": "订单列表为空",
  "apis": {
    "get-orders": {
      "status": 200,
      "data": "empty"
    }
  }
}
```

**`projects/<project-id>/data/<api-id>/<variant>.json`** — 返回值 body · 按接口聚合的业务 JSON。文件内容就是响应体本身，不含 status / delay / headers。

```json
{
  "code": 0,
  "data": []
}
```

### 6.3 接口条目与返回值

一份对外生效的 mock 响应由 **Scene 条目 + data 文件** 合成：

| 来源 | 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- | --- |
| Scene 条目 | `status` | number | 否 | HTTP 状态码，如 200 / 404 / 500，默认 200 |
| Scene 条目 | `delay` | number | 否 | 延迟毫秒数（模拟慢接口），默认 0 |
| Scene 条目 | `headers` | object | 否 | 响应头键值对。未设 `Content-Type` 时默认 `application/json` |
| Scene 条目 | `data` | string | 是 | variant 名，对应 `data/<api-id>/<variant>.json` |
| data 文件 | （文件内容） | any | 是 | 响应体，可为 JSON 对象 / 数组 / 字符串 / `null` |

这是最小完备的结构：**status + body 覆盖正常/异常场景，delay 覆盖慢接口场景，headers 覆盖自定义头**。HTTP 语义留在 Scene，业务 body 留在 `data/`，同一份 body 可以被不同 status / delay 的条目引用。

Scene 的 `apis` 里声明了某接口、但未设 `data`、或对应 variant 文件不存在时：该接口**不算生效路由**，管理面板标记「未设置返回值」；请求不会返回空 body 造成静默误导，而是走未命中逻辑（透传或 404）。

### 6.4 隔离与复用

`data/` 是返回值池，复用是能力，覆盖是风险。默认行为仍对齐「互不覆盖」：

1. **新建条目默认新建 variant**。名称可用语义名（`empty`）或 scene-id（`normal-order`）。不要默认指向已有文件。
2. **「复制其它 Scene 的返回值」= 复制文件**。生成新 variant，再写入本 Scene 的 `data` 字段。
3. **编辑已共享的 variant 时先 fork**。引用计数 > 1 时，保存先复制成新文件再改，避免改 A 把 B 一起改掉。面板展示「此数据被 N 个 Scene 引用」。
4. **显式共享才共用同一文件**（例如多个 Scene 都指向 `get-orders/empty`）。共享是选择，不是默认。

引用计数从本项目所有 `scenes/*.json` 的 `apis.*.data` 汇总。删除 Scene 只删 Scene 文件；variant 不再被任何 Scene 引用时，面板提示清理，**不自动删除**（避免误删手改的备用数据）。

### 6.5 数据维护操作

| 操作 | 文件变化 | 说明 |
| --- | --- | --- |
| **新建项目** | 新增 `projects/<id>/`，写入 `project.json` + 空 `apis.json` / `scenes/` / `data/` | 同时生成该项目 whistle 规则 |
| **删除项目** | 删除 `projects/<id>/` 整个目录 | 二次确认；同时移除 whistle 规则 |
| **新增接口** | 编辑项目 `apis.json`，追加一条接口定义 | 项目内注册一次，该项目所有 Scene 可引用 |
| **新建 Scene** | 新增项目 `scenes/<id>.json` | 文件名即 Scene ID，`apis` 为空对象 |
| **设定返回值** | 改 Scene 条目 + 新建/编辑 `data/<api-id>/<variant>.json` | HTTP 语义写 Scene，body 写 data 文件 |
| **修改返回值** | 编辑对应 data 文件；共享时先 fork | 保存即生效，mock 服务热加载，无需重启 |
| **复制其它 Scene** | 复制 data 文件为新 variant + 写入本 Scene 引用 | 默认隔离，不共享同一文件 |
| **切换 Scene** | 只改 `project.json` 的 `activeScenes` | 所有 Scene JSON 与 data 文件原样保留 |
| **删除接口** | 从 `apis.json` 移除 + 清理各 Scene 引用与 `data/<api-id>/` | mock 服务校验引用，提示哪些 Scene 受影响 |
| **删除 Scene** | 删除 `scenes/<id>.json`；若在激活列表中则一并移除 | 只删该 Scene；孤立 data 文件提示清理 |

### 6.6 热加载与坏文件

- 监听 `mocks/` 目录（含子目录）。文件保存后重新加载受影响的项目 / 接口池 / Scene / data / 配置，目标在 200ms 内对新请求生效。
- 某 JSON 语法错误或字段非法：**保留该文件上一份合法内容继续服务**，并在管理面板顶部显示错误（文件路径 + 原因）。服务进程不退出。单个 data 文件损坏只影响引用它的接口，不影响其它 Scene 与其它项目。
- 某 `project.json` 损坏：只停用该项目（其规则不再下发），其它项目继续服务。`config.json` 整体损坏同理；若从未成功加载过，则启动失败并打印路径，避免带着空配置静默运行。

**为什么这样设计能解决痛点**

- **不丢失**：同接口多场景 = `data/` 下多个独立 variant，切换不删文件，数据天然保留
- **不繁琐**：接口池按项目集中注册，Scene 文件只做组合，返回值按接口聚合，结构清晰、可检索、可 git 管理
- **不散落**：代理配置收拢到项目（域名对 + 一条规则），不再散落在 whistle 规则与备注里
- **可复用**：空列表、校验失败等 body 可被多个 Scene 显式引用，不必复制粘贴；默认仍隔离
- **可共享**：所有数据是纯 JSON 文件，提交到 git 即团队共享，新成员 clone 即拥有全部项目与 mock 场景
- **可 diff**：改 Scene 引用与改 body 分属不同文件，git diff 能分清「换了哪份数据」还是「改了数据内容」
- **热加载**：修改 Scene 或 data 文件保存即生效，mock 服务自动监听文件变化，无需重启

## 7. 匹配、透传与激活

### 7.0 项目定位（先于接口匹配）

请求进入 mock 服务后，**先按 host 定位项目，再在该项目内匹配接口**：

1. 取请求的 host，与所有项目的「被代理域名」比对，命中即归属该项目。
2. 若请求是由全局 `matchPatterns`（如 `/api/`）带进来的、host 不属于任何项目，则归到「当前选中项目」，保证单一前缀接入也能工作。

### 7.1 请求匹配规则

只有「所属项目当前激活 Scene 中、且已设置返回值」的接口会进入该项目生效路由表（条目含 `data` 且对应 variant 文件存在）。一次请求按以下规则在项目内匹配：

1. **method 精确相等**（大小写不敏感，`GET` = `get`）。
2. **path 匹配 URL 模式**。支持 `:param` 单段参数（`/api/users/:id` 匹配 `/api/users/42`，不匹配 `/api/users` 或 `/api/users/42/orders`）。
3. **忽略 query string**。`GET /api/orders?page=1` 与 `GET /api/orders` 视为同一接口。query 匹配不做一期能力，避免规则爆炸。
4. strip 掉转发带来的 host，只比 path。whistle 把 `https://microcredit-ms-test-c.jhjj.paas.test/api/orders` 转到本机后，按 `/api/orders` 在该项目路由表内匹配。

| 请求 | 接口模式 | 结果 |
| --- | --- | --- |
| `GET /api/users/1` | `GET /api/users/:id` | 命中 |
| `GET /api/users` | `GET /api/users/:id` | 不命中 |
| `GET /api/orders?page=1` | `GET /api/orders` | 命中（忽略 query） |
| `POST /api/orders` | `GET /api/orders` | 不命中 |

若两个**不同 api-id** 的 URL 模式都能匹配同一请求（例如 `/api/users/:id` 与 `/api/users/:userId`），按「静态段更多、模式更具体」者优先；仍并列则取接口池中先注册者，并在面板提示潜在歧义。这是匹配层问题，**不走 Scene 冲突弹窗**（冲突弹窗只处理「同一 api-id 被两个激活 Scene 同时引用」）。

### 7.2 未命中时的透传

未命中该项目生效路由的请求，**按所属项目的配置**处理：

- 项目配了「代理到的域名」（`target`）→ 把 method、path、query、body 及必要请求头转发到该上游，把上游响应原样返回（混合联调）。例如未 mock 的接口打到 `http://localhost:8889`。
- 项目未配 `target` → 按全局 `unmatched`：默认 `passthrough` 回浏览器原始地址；`404` 则返回明确未 mock 的 404，避免浏览器看到空白当成功。
- 透传超时默认 30s，失败时返回 `502` 并带上游错误摘要，便于判断是 mock 没配还是真实环境挂了。

透传时不转发 hop-by-hop 头（`Host`、`Connection` 等），`Host` 改为 `target` 的 host。

### 7.3 启动 Scene

启动一个 Scene = 把它加入**所属项目**的激活集合，其下**已设置返回值**的接口进入该项目生效路由表：whistle 把这些接口转到 mock 服务后返回各自设定值，**同时生效、无需逐个配置**。

- **未被任何激活 Scene 覆盖的接口** → 透传到项目 target（「部分 mock + 部分真实」）
- **切换 Scene** = 换一整套接口代理组合，瞬时生效，上一套 Scene 的返回值不丢（Scene JSON 与 `data/` 文件全部保留）
- 激活集合写入项目 `project.json.activeScenes`，重启服务后自动恢复，免去每天重新勾选
- 不同项目的激活互不影响：A 项目激活「下单异常流」不影响 B 项目的任何路由

### 7.4 多 Scene 同时激活与冲突

支持同一项目在同时刻激活多个 Scene，不同业务流程的接口可并行生效。例如同时激活「登录流程 Scene」与「商品列表 Scene」，两组接口的代理同时工作。

> **冲突处理规则（重点）**
>
> 同时激活多个 Scene 时，若**新激活的 Scene 与已激活的 Scene 存在接口重合**（同一 api-id 出现在该项目两个激活 Scene 中），则触发告警，由用户决定启用哪个：
>
> - 系统列出冲突的接口清单（含各 Scene 下 status / 摘要），提示用户二选一
> - 用户选择保留新 Scene → **所有与之冲突的旧 Scene 关闭激活**（其接口代理失效）
> - 用户选择保留旧 Scene → **新 Scene 不进入激活集合**（不生效）
> - 无重合 → 新 Scene 直接追加激活，不影响已激活的 Scene
>
> 核心原则：**冲突接口互斥，按 Scene 整组二选一，不按接口拆开叠加**。避免同一接口被两个 Scene 同时定义返回值造成歧义，也避免「半个 Scene 生效」的碎片状态。被弃用的 Scene 只是关闭激活，本身和所引用的 data 文件仍然保存，下次可重新激活。冲突判定只在同一项目内进行，跨项目不冲突。

边界补充：

- 新 Scene 同时与多个已激活 Scene 冲突：弹窗列出全部冲突对；选「激活新 Scene」则关闭所有冲突的旧 Scene，**与新 Scene 无交集的已激活 Scene 保持不动**。
- 关闭某个已激活 Scene：直接从激活集合移除，不弹冲突窗。
- 文件被手改导致激活集合本身已冲突（例如两个人 merge 了 `project.json`）：服务启动或热加载时拒绝加载该项目的激活集合，面板强制进入冲突解决，在解决前该项目不对外提供歧义路由。
- 不做「按接口挑选保留」——那会让激活状态无法用 Scene 来理解，违背「启动 Scene = 整组生效」。

## 8. 与 whistle 的集成

whistle 不再存储任何 mock 数据，**代理规则按项目维度生成**：每个项目一条「被代理域名 → scene-mock 服务」的规则。切换 Scene **不改规则**；只有新建 / 删除项目、或修改项目的被代理域名时，规则才随之增减。

### 8.1 项目规则

每个项目生成一条 whistle 规则（示例为 whistle 插件短协议形态；独立服务形态则为转发到 `http://127.0.0.1:3456`）：

```
# 项目：微贷后端 · 被代理域名进 scene-mock，未命中由服务透传到 http://localhost:8889
microcredit-ms-test-c.jhjj.paas.test scene-mock://
```

多个项目即多行，与全局 `matchPatterns`（如 `/api/`）叠加，去重后统一下发。被代理域名可带协议书写，规则里只保留 host。

### 8.2 为什么不按接口生成多条规则

按接口池逐条生成 whistle 规则，看起来更精确，但会把「当前 mock 了哪些接口」绑回 whistle：切 Scene、加接口都要重新粘贴规则，重新引入维护成本。按项目转发把决策权留在 mock 服务，才能做到「切 Scene 瞬时生效、whistle 零操作」；项目数远少于接口数，规则维护量可控。

### 8.3 职责重新划分

| | 传统方式 | scene-mock 方式 |
| --- | --- | --- |
| **whistle** | 转发 + 存数据（values） | 仅按项目转发（一项目一规则） |
| **mock 服务** | — | 项目路由、匹配、返回、透传、Scene 生命周期 |
| **代理配置** | 散落在规则与备注 | 项目内聚：被代理域名 + 代理到的域名 |
| **接口数据** | whistle 内扁平变量 | 项目接口池结构化注册，Scene JSON 引用 `data/` 中的返回值 |
| **切场景** | 改 values，旧数据被覆盖 | 改项目激活集合，文件全部保留 |

## 9. Web 管理面板

面板是主操作面，和手改 JSON 等价。目标：不打开编辑器也能完成日常联调（建项目、建 Scene、改返回值、激活、处理冲突）。

面板**不设全局「当前项目」**：Scene 管理、接口池首页即为跨项目聚合列表（按项目名称、名称关键词查询），从列表行或项目管理页进入单个项目管理——无需关心「现在激活的是哪个项目」，各项目数据随时可操作。

| 屏幕 | 说明 |
| --- | --- |
| **项目管理** | 项目列表：名称、被代理域名 → 代理到的域名、Scene 数、激活状态。新建 / 编辑 / 删除项目，并从每行进入该项目的 Scene 管理与接口池。每个项目一卡片或一行，域名对并排展示。项目管理的唯一入口（配置页不再重复提供）。 |
| **Scene 管理** | 首页即跨项目聚合列表：项目、Scene 名称、接口数、激活状态，查询项为**项目名称 + Scene 名称**；行操作进入单项目管理页。单项目页内：一键激活 / 关闭；行操作含**复制 Scene**（生成副本，data 复制为新 variant）。顶部统计：Scene 总数、已激活、接口总数、当前冲突。入口：新建 Scene。 |
| **Scene 详情** | 元信息（名称 / 描述 / ID / 状态）+ 接口条目表（method、URL、status、delay、data variant / 文件路径）。可添加/移除接口、编辑返回值、复制该项目 whistle 规则。 |
| **接口池** | 首页即跨项目聚合列表：项目、method、URL、描述、被引用 Scene 数，查询项为**项目名称 + 接口关键词**；行操作进入单项目接口池。单项目页内：注册 / 编辑 / 删除。删除前展示引用清单。**展开引用清单时可逐 Scene 切换激活开关**（与 Scene 列表开关同一状态，方便「这个接口在哪些 Scene 生效」一目了然地调整）。 |
| **响应编辑器** | 针对「某 Scene × 某接口」。可改 status、delay、Content-Type；JSON 编辑 body（格式化）。status / delay / headers 写回 Scene JSON，body 写回 `data/<api-id>/<variant>.json` 并热加载。若 variant 被多个 Scene 引用，保存时 fork。 |
| **冲突告警弹窗** | 激活时若接口重合：列出冲突接口及两侧返回摘要（status / body 预览）。两个主操作：「激活新 Scene（关闭冲突的旧 Scene）」「保持现状」。脚注：数据不丢失。 |
| **全局配置** | 工作区路径、`matchPatterns`、未命中默认策略、复制 whistle 规则。展示热加载错误与运行时状态（各项目激活 Scene、HTTPS 抓包提示、孤立 variant）。不含项目管理，项目的增删改统一在「项目管理」页完成。 |

交互原则：

- **项目是第一层导航**，Scene / 接口数据按项目隔离，但从聚合列表可一键进入任意项目——这与「代理基于项目维度」的模型一致。
- **激活是 Scene 列表上的开关**，不是藏在详情里的次要操作——这是最高频动作。
- 返回值编辑默认在面板完成；同时显示 Scene 文件路径与 data 文件路径，并展示 variant 引用计数，方便「偶尔手改、git diff」。
- 破坏性操作（删项目、删接口、删 Scene）二次确认，并写清影响范围；删 Scene 不自动删孤立 data 文件；删项目会列出其下全部 Scene 与接口数。

## 10. 典型工作流

```
启动服务 → 绑定 mocks 目录 → 新建/选择项目（配域名对）→ 接入 whistle → 项目下建 Scene → 设返回值 → 启动激活 → 冲突则二选一
```

1. **启动服务**：本地拉起 scene-mock，打开管理面板
2. **绑定 mocks 目录**：数据落在业务仓库，可 git 共享
3. **新建/选择项目**：填被代理的域名与代理到的域名，规则自动生成
4. **接入 whistle**：确认插件规则已生效（或复制规则手动粘贴）
5. **项目下建 Scene**：按业务流程建多个 Scene 并设返回值
6. **启动激活**：打开 Scene 开关，该项目接口代理同时生效
7. **冲突则二选一**：多 Scene 接口重合时整组切换

**对比传统方式**：异常流测试时，传统方式要逐个改 values、测完再逐个改回，极易遗漏；scene-mock 只需切到对应 Scene，测完切回，零数据丢失风险。换联调后端时，传统方式要逐条改 whistle 规则与 values；scene-mock 只需切到对应项目，规则与数据都已在该项目下就绪。

日常增量：新接口先注册进项目接口池，再按需加入相关 Scene；新异常态新建一个 Scene，或用「复制 Scene」从「正常」一键生成副本（全部 data 复制为新 variant）再改差异字段即可；新后端域名新建一个项目，填好域名对即可开始。

## 11. 功能范围、优先级与价值

### 11.1 一期（P0）· 可完成日常联调

| 优先级 | 能力 | 验收要点 |
| --- | --- | --- |
| P0 | 项目 CRUD | 名称 + 被代理域名 + 代理到域名；host 唯一；删除前展示影响；规则随项目增减 |
| P0 | 接口池 CRUD | method + URL 模式 + 描述；id 项目内唯一；删除前展示引用 |
| P0 | Scene CRUD 与接口条目 | 项目内建/改/删 Scene；从项目接口池添加/移除；复制其它 Scene 的返回值为新 variant；**整 Scene 复制生成副本（data 复制为新 variant 集）** |
| P0 | 返回值编辑 | 面板与 JSON 双通道；status / delay / headers 写 Scene，body 写 `data/`；共享 variant 编辑时 fork |
| P0 | 激活 / 关闭 Scene | 项目内多 Scene 并行；状态写入 project.json，重启恢复 |
| P0 | 冲突检测与二选一 | 按 api-id 重合告警（项目内）；整组关闭，不按接口拆分 |
| P0 | 项目定位 + 请求匹配 | 按 host 定位项目；项目内 method + path 匹配，`:param`，忽略 query |
| P0 | 未命中透传 | 项目 target 转发；未配置则回源或明确 404 |
| P0 | 热加载 | 保存即生效；坏 JSON 不拖垮进程，面板报错 |
| P0 | 按项目生成 whistle 规则 | 一键复制 / 自动下发；切 Scene 不必改规则 |
| P0 | Web 管理面板 | 项目管理、Scene 列表/详情、接口池、响应编辑器、冲突弹窗、全局配置 |

### 11.3 非功能要求

- **启动快**：无重依赖，秒级拉起；默认只绑 127.0.0.1。
- **稳**：单个 data 文件损坏不影响其它接口；某个 Scene JSON 损坏只停用该 Scene；某个 project.json 损坏只停用该项目；服务不因热加载失败而退出。
- **可预期**：端口被占、JSON 非法、激活集合自相冲突、项目 host 重复——全部显式报错，不静默降级。
- **数据即文件**：不引入数据库；git 是唯一共享机制。

### 11.4 价值对比

| 维度 | 传统 whistle values | scene-mock |
| --- | --- | --- |
| 数据丢失风险 | 高（场景覆盖） | 消除：同接口多 variant 独立保存在 `data/`，Scene 只引用 |
| 接口切换成本 | 高（逐个改 values） | 零成本：启动 Scene 批量激活 |
| 多域名代理管理 | 散落（规则 + 备注混排） | 内聚：项目 = 域名对 + 一条规则 |
| 换联调环境成本 | 高（逐条改规则） | 零成本：多项目并存，按域名各自路由，无需切换 |
| 冲突可感知 | 无（静默覆盖） | 告警：重合接口整组二选一 |
| 接口可维护性 | 低（扁平堆叠） | 结构化：项目接口池注册 + Scene 组织 |
| 数据可追溯 | 无（whistle 内不可 git） | 可 diff：纯 JSON 文件，git 精准追踪 |
| 团队可共享 | 不支持 | 支持：mock 目录提交 git，clone 即用 |
| 混合联调 | 不支持 | 支持：未覆盖接口透传到项目 target |
| 与现有工具兼容 | — | 无缝：whistle 只加项目规则 |

### 11.5 成功标准（一期）

- 从「正常下单」切到「下单异常流」并看到对应返回，**不超过一次点击 / 一次开关**，且正常 Scene 的 JSON 与所引用的 data 文件原样保留。
- 新成员 clone 仓库、启动服务、接入 whistle 后，**5 分钟内**能跑通已有项目的已有 Scene。
- 两个项目（两个被代理域名）同时代理时互不干扰，各自命中各自的 Scene，未命中各自透传到各自 target。
- 同项目同时激活两个无交集 Scene 时两组接口都生效；有交集时必须经过确认，不会静默覆盖。

## 12. 方案边界、风险与后续演进

### 当前边界

- 面向**前端联调阶段的 mock 接口代理**，非全量接口测试平台，非接口文档系统。
- mock 返回值与代理配置以纯 JSON 文件维护在本地 `mocks/`：项目配置在 `projects/<id>/`，Scene 定义在项目 `scenes/`，业务 body 在项目 `data/`，支持手动编辑 + Web 面板管理双通道。
- 需本地启动一个轻量 mock 服务；依赖开发者本机已有 whistle（或同类代理）。
- 一期不覆盖：WebSocket、按 query / header 分支、HTTPS 终结、动态模板、云端托管。

### 已知风险与对策

- **项目规则过宽或过窄**：被代理域名的所有请求都会进 mock。未 mock 的依赖项目 target 正确；配错会表现为「该域名全挂」。对策：项目卡片强提示 target 含义；透传失败返回 502 而非空白。
- **项目 host 重复**：两个项目抢同一个被代理域名会导致路由歧义。对策：保存时校验 host 唯一，重复直接拒绝并提示冲突项目。
- **matchPatterns 带进来的未知 host**：无法按 host 定位项目。对策：归到当前选中项目并在运行时面板提示；建议优先用项目规则而非裸前缀。
- **接口 id 与文件名耦合**：重命名会牵动 `data/<api-id>/` 目录及所有 Scene 引用。对策：面板把改 id 做成显式「重命名」并级联改文件与引用；文档建议用稳定语义 id。
- **共享 variant 误改覆盖**：多个 Scene 指向同一 data 文件时，手改会同时影响它们。对策：面板展示引用计数；从面板编辑时默认 fork；文档约定手改共享文件前先确认引用。
- **激活状态进 git 可能互相覆盖**：`activeScenes` 是个人联调状态。对策：建议 `project.json` 中激活列表不提交，或提供 `*.local.json` 覆盖（P1）；一期在文档中约定「各人本地改、不要把个人激活状态推进主干」。
- **与真实环境 cookie / 鉴权**：透传需要带上原请求头。对策：默认转发 `Cookie` / `Authorization`；不在 mock 层做登录态模拟（可用独立「登录 Scene」返回固定 token）。

### 演进方向

- **OpenAPI / Swagger 批量导入**：从接口文档一键生成项目接口池
- **whistle 规则自动同步**：通过插件接口免手动粘贴规则
- **Scene 继承/复用**：Scene D 可引用 Scene A 的全部条目再覆盖其中若干
- **项目模板 / 复制项目**：以既有项目为底克隆一套配置，快速接入新环境
- **mock 模板语法**：返回值 body 支持 `{{$random.name}}`、`{{$request.params.id}}` 等动态生成
- **冲突智能建议**：告警时给出「保留哪个 Scene」的推荐依据
- **命中日志与 X-Mock-Scene**：可观测、可被脚本按次覆盖，而不破坏「Scene 整组激活」模型
